# Phase 1 算法审查报告 — Helldivers 2 血条识别

> 创建：2026-07-18  
> 用途：审查 `Phase 1` 血条识别方案（方案 A：纯像素分析），指出潜在问题、遗漏风险和改进建议，供 Claude Code / 工程实现参考。

---

## 0. 审查结论摘要

- 方案 A 适合作为 `Phase 1 MVP`，但不能只做“固定 ROI + 单一亮像素阈值 + 全屏滤镜判断”。
- 真正的风险不在性能，而在 `鲁棒性` 和 `误判控制`。
- 推荐升级为：
  - `固定 ROI + 主条 inner ROI`
  - `HUD 锚点校验`
  - `颜色 + 亮度 + 纹理混合特征`
  - `跨帧状态机`
  - `unknown / 拒识机制`
- 当前阶段 `不建议直接上 YOLO`，先做规则法 MVP，再根据真实视频误判情况决定是否升级。

## 1. 已知事实

基于当前视觉分析，已知以下事实可作为 Phase 1 的初始设计输入：

- 游戏分辨率：`1920x1080`
- 血条固定 ROI：`(97, 943) - (307, 967)`
- 主条本体初始估计：`(106, 949) - (298, 958)`
- 血条为连续长条，右侧斜线纹理代表 `已消耗`
- 消耗方向：`从右往左`
- 治疗恢复方向：`从左往右`

四类状态特征：

| 状态 | 血量估计 | 血条表现 | 全屏滤镜 | 特殊特征 |
|------|----------|----------|----------|----------|
| 满血 | ~100% | 近白/米白填满 | 无 | — |
| 受伤 | ~45-48% | 左亮右暗，亮填充明显缩短 | 红色强烈 | — |
| 死亡 | ~0% | 无亮填充，仅暗红底色 | 红色极浓 | 中央“阵亡”+ 骷髅 |
| 治疗 | ~3-8% | 少量亮残余 + 大面积暗红 | 青蓝色边缘 | 角色注射动作 |

## 2. 总体风险评级

| 审查项 | 风险评级 | 说明 |
|------|------|------|
| 固定 ROI 可靠性 | 高 | 分辨率、HUD 偏移、采集方式变化都会破坏假设 |
| 纯 RGB 阈值识别 | 高 | 红屏/青蓝滤镜会污染血条本身 |
| 单帧状态判定 | 高 | 受伤、治疗、死亡存在动画与过渡帧 |
| 全屏滤镜辅助判断 | 中 | 可用，但不能单独作为主判断依据 |
| 逐列扫描性能 | 低 | ROI 很小，分析成本极低 |
| Phase 1 可落地性 | 中高 | 需要增加锚点校验、混合特征和拒识机制 |

## 3. 可靠性审查

### 3.1 固定 ROI 在什么情况下会失效

风险评级：`高`

固定 ROI 在以下场景下容易失效：

- 分辨率不是 `1920x1080`
- 窗口化 / 无边框模式导致采集画面偏移
- OBS、录屏软件、远程桌面造成裁切或缩放
- HUD 安全边距、UI 缩放被用户调整
- 游戏更新后 UI 微调
- 截图来源不是原始帧，而是经过压缩/二次处理

建议：

- 不要只保存一组 ROI，至少支持 `按分辨率分 profile`
- 启动时加入 `HUD 锚点校验`
- 当锚点不匹配时，输出 `unknown`，不要继续硬判

推荐最小锚点：

- 左下 `A1` 方框
- 血条左右端帽
- 血条左侧竖线框

### 3.2 红色滤镜对血条颜色污染是否严重

风险评级：`高`

污染是严重的，原因如下：

- 红屏会同时影响亮填充和暗空槽
- 受伤时“亮填充”从米白变成粉红/红
- 死亡时“空血底色”也会变成整体偏红
- 因此不能简单把“亮色”当成血量、“暗色”当成空槽

### 3.3 HSV 能否规避颜色污染

风险评级：`中`

结论：`只能部分缓解，不能根治`

原因：

- 红屏会同时改变 `Hue / Saturation / Value`
- 满血白条在红屏下不再稳定是白色
- 低血暗红与死亡暗红在 HSV 上可能重叠

建议：

- 优先试 `Lab` 或 `YCrCb`
- 将血条识别从“纯颜色阈值”升级为“颜色 + 亮度 + 纹理”

### 3.4 满血但红屏会不会误判

风险评级：`中`

会不会误判，取决于你把“受伤”定义成什么：

- 如果“受伤状态”定义为 `血量低于阈值`，则不会因为红屏单独误判
- 如果“受伤事件”定义为 `红屏出现`，则很容易误报

建议：

- 将 `状态` 与 `事件` 分离
- `状态`：看稳定血量
- `事件`：看跨帧血量突降、滤镜突增、随后确认

## 4. 精度审查

### 4.1 逐列扫描如何定义“有效血量像素”

风险评级：`高`

不建议定义为：

- “亮于某阈值的像素”
- “R 值高于某阈值的像素”

因为：

- 满血为米白
- 受伤填充为粉红/红
- 空槽为暗红斜纹
- 三者都可能被滤镜改变

建议采用 `每列聚合特征`，而不是逐像素硬阈值：

- `p90_luma`：该列亮度 90 分位
- `mean_redness`：如 `R - max(G, B)` 或 `Cr`
- `texture_energy`：局部纹理强度
- `diagonal_gradient`：空槽斜纹梯度特征
- `local_variance`：局部方差

推荐思路：

1. 只分析主条本体 `inner_bar_roi`
2. 对每一列提取上述特征
3. 计算 `filled_score`
4. 按分数判断该列是 `filled / empty / uncertain`
5. 对列序列做 1D 平滑后再求血量边界

可用的经验公式：

```text
filled_score
  = a * p90_luma
  + b * redness
  - c * diagonal_gradient
  - d * local_variance
```

### 4.2 血量百分比如何映射

风险评级：`中`

建议：`线性映射`

前提是：

- 只对主条有效宽度映射
- 不把外框、端帽、抗锯齿边缘算进去

推荐公式：

```text
health_pct = (x_last_filled - x_fill_min) / (x_fill_max - x_fill_min)
```

其中：

- `x_fill_min`：主条最左有效起点
- `x_fill_max`：主条最右有效终点
- `x_last_filled`：最右侧稳定 filled 列

建议加入边界死区：

- `< 2%` 视为 `0%`
- `> 98%` 视为 `100%`

### 4.3 是否有血条动画影响读数

风险评级：`中`

高概率有以下过渡影响：

- 受击后血条平滑缩短
- 治疗后血条平滑回升
- 某些帧先出现滤镜，再出现血量变化

因此单帧状态不可完全相信。

建议：

- 保留 `raw_health_pct`
- 额外计算 `stable_health_pct = EMA(raw_health_pct)`
- 事件检测看 `raw delta`
- 状态判定看 `stable_health_pct`

### 4.4 治疗判定是否只靠滤镜

风险评级：`高`

不建议只靠“青蓝滤镜”判定治疗。

更可靠的治疗确认应满足至少两项：

- 青蓝边缘滤镜出现
- 角色存在注射动作线索
- 刺激针相关 UI 有辅助信号
- 血量在 N 帧内明显上升

## 5. 遗漏审查

### 5.1 纯像素方案遗漏的关键边界情况

风险评级：`高`

当前方案遗漏了以下关键问题：

- HUD 是否真实存在
- 菜单、过场、黑屏、载入画面
- 录屏压缩造成的色块和模糊
- 爆炸/火焰导致左下区域被强烈染红
- HDR / 自动曝光 / gamma 差异
- 多语言 UI 导致文字检测失效
- 治疗动作与真正回血结果之间的时间差

### 5.2 需要额外检测的 UI 元素

风险评级：`中`

建议加入以下辅助检测：

- `A1` 武器槽锚点
- 血条左右端帽
- 左下武器/弹药 HUD 是否存在
- 中央“阵亡”区域
- 骷髅图标区域
- 刺激针数量区域

### 5.3 全屏特效会不会导致误判

风险评级：`中`

会，尤其是：

- 爆炸强光
- 火焰反光
- 烟雾 / 雾气降低对比度
- bloom 让白条溢出
- 受伤红屏覆盖整个 HUD

建议：

- 全屏滤镜采样不要只采 1 个点，要采 `多边缘区域`
- 对红色和青蓝滤镜分别输出 `score`
- 如果滤镜得分异常而 HUD 锚点也异常，则直接 `unknown`

### 5.4 死亡是否只看血量归零

风险评级：`高`

不应只看 `health_pct ≈ 0`。

正确做法应结合：

- `health_pct ≈ 0`
- 中央死亡提示区域
- 骷髅图标区域
- 极强红屏

这样能避免把“极低血但未死”误判为死亡。

## 6. 性能审查

### 6.1 逐列扫描 210px ROI 的耗时

风险评级：`低`

结论：分析成本非常低，瓶颈通常不在检测，而在截图。

粗略估计：

- Python 双层像素循环：约 `0.5ms - 3ms`
- NumPy 向量化：通常 `< 0.2ms`
- OpenCV + NumPy：同级，且更适合做颜色空间和梯度分析

### 6.2 Python 中用哪种库最快

建议排序：

1. `NumPy + OpenCV`
2. `NumPy`
3. `PIL` 仅用于离线验证，不建议作为实时主路径

截图侧建议：

- 若追求低延迟：`dxcam`
- 若追求简单稳定：`mss`

总结：

- 分析：`OpenCV / NumPy`
- 采集：`mss` 或 `dxcam`

## 7. 改进方向

### 7.1 什么时候该切换到模板匹配

风险评级：`中`

当出现以下问题时，优先考虑模板匹配，而不是 YOLO：

- ROI 偶尔漂移
- HUD 外形稳定
- 分辨率档位有限

建议用途：

- 用模板匹配定位或校验 `A1` 区、血条端帽区
- 然后再进入 ROI 内部像素分析

### 7.2 什么时候该切换到 YOLO

风险评级：`中`

只有在以下条件成立时，YOLO 才值得：

- 要支持多分辨率
- 要支持不同 UI 缩放
- 要支持多语言 UI
- 视频来源复杂，ROI 经常变化
- 规则法在真实视频中误判始终压不下去

当前阶段不建议直接上 YOLO。

### 7.3 有没有更好的方案

建议的更优中间方案：

`两阶段规则法`

阶段 1：

- HUD 锚点校验 / 定位

阶段 2：

- 主条内做 1D 血量边界估计
- 辅助做死亡 / 治疗线索检测

另一个可选方案：

- 使用一个轻量 `列分类器`
- 例如逻辑回归 / 线性 SVM / 随机森林
- 输入每列特征，输出 `filled / empty / uncertain`

这样比纯手写阈值更稳，但仍不需要深度学习。

## 8. 实施建议

### 8.1 代码结构建议

当前结构：

```text
config.ini
health_detector.py
screen_capture.py
test_detector.py
```

基础上建议扩展为：

```text
screen_capture.py   # 屏幕采集
roi_locator.py      # ROI 与 HUD 锚点校验
health_detector.py  # 血条主条分析
effect_detector.py  # 红屏/青蓝滤镜/死亡UI检测
state_machine.py    # 跨帧状态与事件
test_detector.py    # 离线回放测试
debug_overlay.py    # 调试可视化
```

### 8.2 config.ini 应包含的参数

建议至少包含：

- 分辨率 profile
- 外层血条 ROI
- inner bar ROI
- 左右端帽忽略宽度
- 血量 0% / 100% 标定坐标
- 颜色空间设置
- filled_score 权重
- 列分类阈值
- 红滤镜采样区域
- 青蓝滤镜采样区域
- HUD 锚点阈值
- EMA 平滑参数
- 事件 debounce 帧数
- 事件 cooldown
- unknown 触发条件
- debug 开关
- 误判帧保存路径

### 8.3 MVP 验收标准是否合理

你的目标：

- 满血 `>= 95%`
- 受伤 `>= 90%`
- 死亡 `>= 99%`
- 治疗 `>= 80%`

结论：

- 作为早期 MVP，方向合理
- 但还缺少 `误报率` 和 `延迟` 约束

建议补充：

- 死亡误报极低
- 残血持续误报极低
- 受伤脉冲触发延迟 `< 150-250ms`
- 治疗确认延迟 `< 500ms`
- `unknown` 帧绝不触发设备

### 8.4 代码级优化建议

- 不要写 Python 双层逐像素 for 循环作为主路径
- 所有图像分析尽量 `NumPy 向量化`
- 先裁 `inner_bar_roi`，再做特征提取
- 每帧只做一次颜色空间转换
- 输出统一结构体，例如：

```python
{
    "health_raw": 0.46,
    "health_stable": 0.48,
    "red_score": 0.72,
    "cyan_score": 0.05,
    "death_score": 0.01,
    "state": "injured",
    "confidence": 0.91
}
```

- `state_machine.py` 只消费检测结果，不直接处理图像
- 加 `debug overlay`，把每帧的 ROI、边界、状态、置信度画出来

## 9. 推荐落地路线

建议按以下顺序推进：

1. 固定 ROI + inner bar ROI + NumPy 向量化
2. 列级亮度/颜色/纹理混合特征
3. HUD 锚点校验
4. red / cyan / death 辅助检测
5. 状态机与 DG-LAB 事件映射
6. 离线回放验证 + 误判样本积累

---

## 10. 最终判断

- 当前方案 A 作为 `最初 MVP` 是可行的
- 但如果直接按“固定 ROI + 亮像素阈值 + 红蓝滤镜规则”实现，`可靠性风险为高`
- 如果升级为：
  - `固定 ROI + 锚点校验`
  - `主条内混合特征`
  - `跨帧状态机`
  - `unknown 拒识`
- 那么 `Phase 1 可行性为中高`，足以支撑第一版联调

不建议现在直接切 YOLO。  
建议先做一个可解释、可调试、可回放验证的规则法版本，把误判类型跑清楚，再决定是否上学习型方案。
